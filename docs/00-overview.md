# 00 — Project Overview

## 1. Problem statement

Meeting rooms in the organization are currently booked informally. This produces:

- **Double bookings** — two teams arrive at the same room at the same time.
- **No visibility** — employees walk the floor looking for a free room.
- **No authority to fix conflicts** — nobody can authoritatively move or cancel a booking.
- **No record** — there is no history of who booked what, or why a meeting was moved.

## 2. Solution summary

A web application where:

- The organization's **office admin** configures rooms (name, capacity, location, equipment,
  availability rules).
- **Employees** sign in with email + password, see room availability on a calendar, and book a
  room for a time slot.
- **Admins** can cancel any booking or **move** it to a different room (or a different time),
  with a required reason.
- The system **emails** the organizer (and optionally attendees) on every relevant event:
  booking confirmed, booking moved, booking changed, booking cancelled, and a reminder before
  the meeting starts.

## 3. Goals

| # | Goal | Measure of success |
|---|------|--------------------|
| G1 | Eliminate double bookings | Zero overlapping confirmed bookings per room, enforced at the database level |
| G2 | Make availability obvious | An employee can find a free room matching their needs in under 30 seconds |
| G3 | Give admins authority | Admin can move or cancel any booking in under 3 clicks, and the organizer is told automatically |
| G4 | Keep everyone informed | Every state change produces an email within 60 seconds |
| G5 | Leave an audit trail | Every create / move / change / cancel is recorded with actor, timestamp and reason |

## 4. Non-goals (explicitly out of scope for v1)

These are listed so there is no ambiguity. Several are in the
[post-v1 backlog](11-delivery-plan.md#post-v1-backlog).

- Desk / hot-desk booking, parking spaces, or equipment loans.
- Catering, visitor management, or facilities ticketing.
- Payment or chargeback for room usage.
- Native mobile apps (the web UI is responsive and works in a phone browser).
- Room display tablets mounted outside rooms with check-in buttons.
- Single Sign-On (SAML / OIDC). v1 is email + password. The data model leaves room for SSO
  later (see [03-data-model.md](03-data-model.md)).
- Multi-tenant SaaS. The system is built for **one organization** — though that organization
  may have many sites ([14](14-multi-location.md)) — and every row is scoped to an
  `organization_id` so multi-tenancy becomes a configuration change rather than a rewrite.

## 5. Actors

| Actor | Description |
|-------|-------------|
| **Employee** | Any staff member with an account. Books rooms, manages their own bookings. |
| **Office Admin** | Manages rooms and all bookings. Can cancel or move anyone's booking. |
| **Owner** | A super-admin who can also manage users and organization settings. In a small org the office admin and owner are often the same person. |
| **System** | Background jobs: sending queued email, sending reminders, expiring old data. |

Full permission matrix: [08-security.md](08-security.md#4-authorization-matrix).

## 6. Glossary

| Term | Meaning |
|------|---------|
| **Booking** | A reservation of one room for one continuous time range by one organizer. |
| **Organizer** | The user who created the booking and who owns it. |
| **Attendee** | A person invited to a booking. May be an internal user or an external email address. Attendees do not own the booking. |
| **Move** | Changing a confirmed booking's room and/or time. The booking keeps its identity and ID; it is not cancelled and recreated. |
| **Series** | A recurring meeting: a rule plus the set of bookings it generates. |
| **Occurrence** | One booking generated by a series. An ordinary booking row that knows which series it belongs to. |
| **Exception** | An occurrence that has been changed independently of its series — moved, or cancelled, on its own. |
| **Horizon** | How far into the future a series materializes actual booking rows. Rolled forward nightly. |
| **Connection** | A user's authorized link to their Google or Microsoft calendar. |
| **Closure** | A time range in which a room cannot be booked (maintenance, cleaning, private event). |
| **Booking window** | How far in advance a room may be booked, and the minimum notice required. |
| **Business hours** | The organization-wide default window during which rooms may be booked. A room can override it. |
| **Outbox** | The database table holding emails that are queued, sending, sent or failed. |
| **Half-open interval** | A time range that includes its start and excludes its end, written `[start, end)`. A booking 09:00–10:00 and one 10:00–11:00 do **not** overlap. |

## 7. Assumptions

These shaped the design. Tell me if any is wrong — several would change the plan materially.

| # | Assumption | Impact if wrong |
|---|-----------|-----------------|
| A1 | One organization, roughly 20–500 employees and 5–50 rooms | Larger scale would push toward PostgreSQL from day one and a dedicated job queue |
| A2 | **Multiple sites, potentially in different timezones.** Each location has one timezone | Now a core assumption, not a tolerance — see [14](14-multi-location.md) |
| A3 | Accounts are created by an admin (invite-based), not open self-signup | Open signup needs email-domain allowlisting and a verification flow |
| A4 | The organization can provide SMTP credentials (Google Workspace, Microsoft 365, or a relay) | Would switch to a hosted API such as Resend or SendGrid — a one-file change behind the mailer interface |
| A5 | English-only UI for v1 | Internationalization would need to be built in from the start rather than retrofitted |
| A6 | Deployed on a single server or container the organization controls | Multi-instance deployment needs a shared session store and a leader-elected scheduler (both noted in [02](02-architecture.md)) |

## 8. Technology summary

A **modular monolith**: Node.js backend and React frontend, one repository, one deployable
process. Full rationale: [02-architecture.md](02-architecture.md).

- **Architecture:** Monolith — Express serves both the JSON API and the built React bundle from the same origin
- **Runtime:** Node.js 24 LTS, TypeScript (strict) throughout
- **Backend:** Express 5, Prisma ORM
- **Frontend:** React 19 + Vite 6, React Router 7, TanStack Query, React Hook Form, CSS Modules
- **Shared:** A `shared/` workspace holding Zod schemas, response types and the permission matrix — used by **both** the server and the client, so the contract cannot drift
- **Database:** SQLite in development, PostgreSQL in production — one schema via Prisma
- **Email:** nodemailer over SMTP, with a persistent outbox table and retry
- **Auth:** Same-origin `HttpOnly` session cookies (no tokens in browser storage), Argon2id hashing
- **Testing:** Vitest (unit), Supertest (API), React Testing Library (components), Playwright (end-to-end)
